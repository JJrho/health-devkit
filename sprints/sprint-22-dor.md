## 1. 需求描述

**範圍定位**：這是 E5 健康行動閉環的最後一個 Feature（4/4），把散落在各模組的資料整合成兩種「離開系統也帶得走」的輸出——看診當下可列印帶去的固定模板摘要（C19），以及完整的個人資料匯出（C20，資料可攜權）。上游 §17 的 CRUD 物件表**沒有**列出「看診摘要」與「資料匯出」，不同於「專業轉介摘要」有明確狀態機——本輪定位為**即時產生的唯讀輸出**，不建立新的可管理物件（見 A128）。

兩項交付：

1. **看診摘要（C19）**：`POST /api/projects/{id}/visit-summary`
   - 固定模板五區塊：背景（`health_profiles`）／期間趨勢（`observations`，日期區間可選）／執行中計畫（`active`／`paused`／`needs_info` 等未終止狀態的 `intervention_plans`，若近期有檢討判斷「需要專業評估」則附註提示並帶出既有轉介摘要內容，銜接 E5-F3）／症狀事件（`symptom_events`，可選日期區間）／想問醫師的問題（使用者當下輸入的自由文字，不落地儲存，見 A133）
   - 使用者以勾選決定要包含哪些區塊＋趨勢與症狀事件的日期區間
   - 伺服器端用既有 `pdf-lib`（非新增套件，見 A129）直接繪製 A4 尺寸 PDF 並回傳，同一份輸出即滿足「可列印」與「PDF 匯出」
2. **資料匯出（C20）**：`GET /api/projects/{id}/export`
   - 回傳一個 ZIP，內含：`data.json`（該專案完整結構化資料：profile／documents metadata／observations／plans 全家族／check-ins／symptom events／reviews／escalation summaries）、`trends.csv`（`observations` 攤平為 CSV）、`documents/` 資料夾（透過既有 `StorageAdapter` 下載的原始上傳檔案）
   - 範圍為單一專案，非帳號整體跨專案匯出（A130）
   - ZIP 封裝改用新增相依套件 `archiver`（A131，Node.js 標準庫僅有 gzip/deflate 原語，無 ZIP 容器格式）

## 2. 使用者角色

專案擁有者（一般使用者）：看診前想帶一份重點摘要去診間；或任何時候想把自己的資料完整帶走（換平台、備份、個資法可攜權）。

## 3. 操作流程

看診摘要：使用者於專案頁面點擊「產生看診摘要」→ 勾選要包含的區塊＋設定趨勢／症狀事件的日期區間 → 填寫「想問醫師的問題」（可留空）→ 送出 → 瀏覽器下載一份 A4 PDF。
資料匯出：使用者於專案頁面點擊「匯出資料」→ 瀏覽器下載一個 ZIP 檔，內含結構化資料、趨勢 CSV 與所有原始上傳檔案。

## 8. 可能影響的舊功能

- 新增相依套件 `archiver`（A131），僅用於本輪匯出功能，不影響既有程式碼路徑
- `pdf-lib` 從純讀取（頁數驗證）擴充為同時用於寫入（PDF 產生），既有 `file-validation.ts` 用法不受影響（不同函式、不同用途）
- 重用既有 `StorageAdapter`／`findOwnedProject`／各模組既有查詢函式，無需修改既有介面簽章

## 10. 範圍排除

- **帳號整體跨專案匯出**——本輪僅單一專案範圍（A130），帳號層級需求留給 E6-F1 視需要重用本端點
- **看診摘要／匯出的歷史記錄或排程**——皆為即時產生，不落地、不可管理（A128／A134）
- **匯出格式以外的選項**（如使用者自訂匯出哪些資料類別）——C20 定義的 JSON＋ZIP＋CSV 组合為固定輸出，不做逐項勾選
- **對匯出或摘要內容做任何 AI 摘要／潤飾**——純結構化資料彙整，不經 LLM，延續 A105／A114／A118 一貫原則

## 11. 假設登記（待 PO 追認）

- **A128（新增，架構決定）**：看診摘要不建立持久化資料表或物件，純粹依當下即時資料動態產生 PDF，不儲存產生記錄。**理由**：上游 §17 主要物件 CRUD 表未列出「看診摘要」（不同於「專業轉介摘要」有明確 `draft／ready／exported／deleted` 狀態機），且 C19 描述為「固定模板…範圍由使用者勾選」，語意上更接近「每次現場產生的報表」而非「使用者長期管理的文件」。
- **A129（新增）**：PDF 產生使用既有相依套件 `pdf-lib`（本專案已用於文件頁數驗證，非新增依賴），伺服器端直接繪製 A4 尺寸頁面內容，不透過瀏覽器 print-to-PDF。**理由**：確保「可列印」與「PDF 匯出」是同一份確定性輸出，且重用既有套件不增加相依面。
- **A130（新增，範圍決定）**：資料匯出範圍為單一專案，非帳號整體跨專案匯出。**理由**：本專案所有資源皆以專案為單位組織（documents／plans／observations 皆掛 `project_id`），單一專案匯出與既有架構一致且可獨立完成於 1 個 Sprint；帳號整體匯出留給未來 E6-F1（帳號刪除鏈，若需要「刪除前建議匯出」）視需要迴圈呼叫本端點逐專案匯出，不在本輪重新設計帳號層級格式。
- **A131（新增，技術選型）**：資料匯出的 ZIP 封裝新增相依套件 `archiver`。**理由**：Node.js 標準庫（`zlib`）僅提供 gzip/deflate 壓縮原語，未內建 ZIP 容器格式封裝；`archiver` 為業界常用、授權寬鬆（MIT）、串流式的 ZIP 產生工具，避免自行實作 ZIP 格式的正確性風險。
- **A132（新增，安全設計）**：匯出的原始檔透過 `StorageAdapter` 於伺服器端下載後直接串接進 ZIP 回應串流，不簽發任何對外可存取的檔案連結。**理由**：比對外簽發短效連結更安全（完全不對外曝露 URL），且與憲法 §1「外部服務經 adapter」介面一致。
- **A133（新增）**：「想問醫師的問題」欄位純粹是使用者在產生看診摘要當下輸入的自由文字，不落地儲存、系統不對內容做任何語意分析、摘要或建議。**理由**：延續 A105／A114／A118「結構化而非語意判讀」一貫原則；且此欄位性質上是使用者的當下提問草稿，儲存反而可能造成使用者誤以為系統會追蹤或處理這些問題。
- **A134（新增，效能範圍）**：大型專案（多份文件／大量結構化資料）的匯出效能本輪不做特別優化，無背景工作佇列或進度顯示，以同步 HTTP 請求／回應完成。**理由**：既有檔案數量與大小上限（C12：單專案 ≤ 200 份文件、單檔 ≤ 20MB）已合理限制最壞情況下的資料量；若未來實測發現效能不足，屬獨立議題另行處理，非本輪臆測需求。
