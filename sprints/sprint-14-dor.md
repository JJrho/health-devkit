## 0. 開工前確認：本輪知識素材現況（重要脈絡）

E4-F1 目前僅有王健宇醫師書籍 2 個試點章節（11/706 頁），且 `status=draft`（未經最終人工校對），`searchKnowledge()` 依設計不會回傳 draft 內容。本輪若打算用「真實內容」示範主張抽取與衝突比對，會遇到兩個實質問題：

1. **內容型態不合**：王醫師書籍是病患衛教敘事文字，不是上游 §13.2 設計時預期的研究型結構化資料（族群／劑量／比較對象／研究類型等欄位，明顯對應學術研究或臨床指引的格式）。把敘事文字「詮釋」套進這些欄位，若詮釋有誤，屬於**語意扭曲**而非單純辨識錯誤——比 E4-F1 查核出的 OCR 品質問題更嚴重（OCR 錯誤是機器辨識失準，語意詮釋錯誤是把作者原意讀錯），直接牴觸憲法 §3。
2. **樣本不足以示範「衝突」**：衝突的定義前提是同一主題至少有 2 個方向不同的主張；目前僅 2 個章節，主題大概率不重疊，無法從真實內容中誠實地生出一組衝突案例。

**本輪傾向**：資料模型與比對／檢索邏輯為主（比照 E4-F1「先把管線做對」的既有原則），示範情境以合成資料為主（比照 Sprint 9–13 已建立的模式），並沿用上游 §29 現成的 Gherkin 範例（「咖啡與骨骼健康來源不一致」）作為合成情境依據，不勉強從真實內容生產衝突案例。真實內容的主張抽取留待後續迭代，且應由 PO 或醫師本人參與判斷，非本輪 AI 單方面詮釋敘事文字。

## 1. 需求描述

**範圍定位**：E4-F2 是「主張」層——把知識來源的切分內容（`knowledge_chunks`）轉換為結構化、可比較的醫學主張（`evidence_claims`），並標記主張間的衝突狀態（七分類，上游 §13.3），供 E4-F3（AI 串流問答）未來查詢與呈現。

本輪**不含**：
- LLM 自動主張抽取（本輪無 LLM API key／串流輸出，純資料模型＋人工／seed script 建立，比照 C3 精神延伸到主張層）
- 衝突判斷的自動化演算法（見 A62，人工標記非系統推論）
- §13.4 AI 呈現邏輯（相對一致／爭議部分等七要求，屬 E4-F3 職責）
- API 路由或 UI（同 E4-F1 模式，E4-F3 尚未建置、目前無消費者）

三項交付：

1. **DB migration**：新表 `evidence_claims`——
   - `id`、`sourceId`（FK `knowledge_sources`，必填）、`chunkId`（FK `knowledge_chunks`，**可為 null**，見 A64）
   - 上游 §13.2 逐字 13 項（除「來源版本」外皆為主張本身內容，見下方逐項對應）：`population`（族群）、`action`（行動或曝露）、`dosage`（份量）、`comparator`（比較對象）、`outcome`（結果）、`studyDirection`（研究方向）、`studyType`（研究類型）、`applicableConditions`（適用條件）、`risk`（風險）、`uncertainty`（不確定性）、`publishedDate`（發布日期）、`sourceVersion`（來源版本快照，integer，見 A66）、`withdrawn`（是否撤回，boolean）
   - `topicKey`（text，**新增分組欄位**，非上游逐字欄位，見 A61）
   - `conflictStatus`（text，nullable，七分類 enum：`consistent`／`different_conditions`／`mixed_evidence`／`insufficient_evidence`／`not_applicable`／`source_outdated`／`source_withdrawn`，對應上游 §13.3 逐字七項）
   - `conflictReason`（text，nullable，衝突原因說明——Stage 7「衝突原因可顯示」要求）
   - `version`、`createdAt`、`updatedAt`
2. **服務層函式**（純函式／查詢，無 API 路由，比照 E4-F1 A58 模式）：
   - `getClaimsForTopic(topicKey): Promise<EvidenceClaim[]>`——依 `topicKey` 取得同主題所有主張，只回傳來源 `status='active'` 的主張（比照 `searchKnowledge()` 安全閘門，`withdrawn` 來源／主張一律排除）
   - 回傳結果依 `conflictStatus` 標記，供未來 E4-F3 判斷是否需要在回答中呈現衝突說明
3. **Seed／測試資料**：合成資料示範至少一組「衝突」情境，沿用上游 §29「咖啡與骨骼健康」範例（同 `topicKey`、2+ 筆 `conflictStatus` 不同的主張），驗證資料模型與查詢邏輯確實可用；不強行用王醫師真實內容示範衝突（見 §0、A63）。

## 2. 使用者角色

同 E4-F1，本輪無終端使用者可見介面；維護者為**系統管理者（PO 本人）**，透過 seed script／DB 直接維護（C3 精神延伸）。

## 3. 操作流程

PO／醫師人工判斷某段知識內容可歸納出的主張與其上游 §13.2 欄位值，並判斷該主張與同主題其他既有主張的關係（衝突狀態，§13.3）→ 寫入 seed script → 執行 seed script 寫入 `evidence_claims` → 未來 E4-F3 呼叫 `getClaimsForTopic()` 取得可用主張與衝突標記。本輪無使用者可見流程。

## 10. 範圍排除

- **LLM 自動主張抽取**——本輪無 LLM API key／串流輸出，純資料模型＋人工／seed script 建立主張內容
- **自動化衝突判斷演算法**——醫學衝突判斷需要語意理解，規則式程式碼無法可靠判斷，勉強做一個看似能分類但實際不準確的演算法比誠實地人工標記更危險（見 A62）
- **§13.4 AI 呈現邏輯**（相對一致部分／爭議部分／研究不同原因等七要求）——需要語言生成能力，屬 E4-F3 職責
- **API 路由／UI**——同 E4-F1 模式，E4-F3 尚未建置，目前無消費者
- **真實王醫師內容的衝突情境示範**——素材不足且型態不合（見 §0、A63），避免為了展示功能而扭曲醫學語意
- **pgvector／語意相似度自動分群 `topicKey`**——本輪 `topicKey` 由人工指定字串，非自動語意分群（承接 E4-F1 A54 向量檢索暫緩的既有範圍排除）

## 11. 假設登記（待 PO 追認）

- **A61（新增）**：新增 `topicKey`（text）欄位作為主張分組鍵。**理由**：上游 §13.2／§13.3 未明文定義「同一主題的多個主張如何分組以利衝突比對」的機制，若無分組鍵，衝突比對將無從進行（需要先知道哪些主張在討論同一件事）。本輪由 PO／seed 作者在建立主張時人工指定（如 `"咖啡攝取與骨質疏鬆風險"`），不做自動分群（語意相似度分群屬未來可能的強化，非本輪範圍）。
- **A62（新增）**：`conflictStatus` 為人工標記，非系統自動判定。**理由**：判斷「證據混合」與「條件不同」的差異需要對研究方法與適用情境的語意理解，規則式程式碼（如比對數值範圍或關鍵字）無法可靠判斷；勉強做一個看似能自動分類、實際不準確的演算法，比「誠實地由人工標記」風險更高（可能誤導使用者、牴觸憲法 §3）。故本輪比照 C3 精神，`conflictStatus` 由 PO／seed 作者依 §13.3 七分類人工指定。
- **A63（新增）**：本輪不強行用真實王醫師書籍內容示範「衝突」情境。**理由**：目前僅 2 章節、內容為病患衛教敘事而非研究型結構化資料，且彼此主題大概率不重疊；若為了展示功能而勉強從敘事文字「詮釋」出研究型 §13.2 欄位（族群／劑量／比較對象等），有扭曲原意的醫療安全風險（屬語意詮釋錯誤，比 OCR 辨識錯誤更難察覺）。本輪示範資料採合成資料為主，沿用上游 §29 現成的「咖啡與骨質疏鬆」Gherkin 範例。真實內容若要建立 `evidence_claims`，留待後續迭代，且需要 PO 或醫師本人參與主張抽取判斷。
- **A64（新增）**：`chunkId` 為 nullable。**理由**：並非每個主張都能精確對應到單一 chunk（可能橫跨多個 chunk，或是對來源整體的摘要判斷），故設為可為 null，但盡量填以利追溯；`sourceId` 為必填保底，確保 Stage 7「每個主張可追溯」的最低要求仍成立。
- **A65（新增）**：本輪不實作 §13.4 AI 呈現邏輯。**理由**：把 `conflictStatus`／`conflictReason` 資料轉譯成使用者可讀語句（相對一致部分／爭議部分／研究不同的可能原因等七要求）需要語言生成能力，屬 E4-F3（AI 串流問答）職責；本輪只負責讓資料「可查詢」，不做呈現文案。
- **A66（新增）**：`sourceVersion` 為建立主張當下的來源 `version` 快照（寫入時複製數值），非動態 join 現在的來源版本。**理由**：上游 §19「AI 報告保存個人資料版本與知識版本」與 §28.6「資料更新後舊報告標示過期」暗示需要記錄主張建立當下所依據的來源版本；若來源之後被更新（version 遞增），舊主張仍應保留其原始依據版本以利未來「是否過期」判斷。過期判斷邏輯本身（比對快照版本與來源目前版本）留待 E4-F3 實作，本輪僅存欄位。
- **A67（新增）**：本輪不新增任何 API 路由。**理由**：比照 E4-F1 A58 模式，E4-F3 尚未建置，`getClaimsForTopic()` 為純服務層函式，直接透過單元測試驗證，供 E4-F3 未來直接呼叫。
