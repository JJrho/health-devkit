## 0. 開工前確認

本輪不涉及新的外部依賴（LLM key 已備妥且驗證可用，見 Sprint 15）。範圍延續 Sprint 15 DOR §10 明確列出的排除項：**UI／`regenerate`／頻率限制（C17）／進階安全過濾**，本輪逐項打磨。

## 1. 需求描述

**範圍定位**：PoC 1/2 已證明核心技術風險（引用驗證端到端）可行，本輪把 Sprint 15 刻意排除的產品化必要項補齊，讓 E4-F3 具備可讓真實使用者操作的完整體驗，同時不擴大到 E4-F3 範圍以外（不含 `reports`、不含知識庫內容擴充、不含進階語意驗證）。

四項交付：

1. **UI**：新增 `/projects/[id]/chat` 對話頁（上游 §6.2 十個工作區頁面之一，串流問答）——
   - 對話列表（若無對話則顯示建立新對話按鈕）
   - 訊息串：使用者訊息＋助理訊息（SSE 即時顯示 `content_delta` 累積文字）
   - 引用清單：完成後列出 `message_citations`，可回查（比照既有趨勢頁 drill-down 精神，點擊可查看來源文字）
   - 安全提示 banner：`safety_notice` 事件觸發時於畫面顯著位置顯示提醒文字（非攔截，僅提示，A73／A76 既定原則延伸）
   - 取消按鈕：串流中可按下觸發 cancel
   - WCAG 2.2 AA：鍵盤可操作、不對每個 token 觸發螢幕閱讀器朗讀（技術選型 §11.3 既定要求）、色彩不作為唯一提示手段
2. **`GET /api/projects/{id}/conversations`**：列出專案內對話（依 `updatedAt` 遞減，不分頁——MVP 資料量小，比照既有 `documents`／`observations` 列表簡單模式）
3. **`regenerate`**：`POST /api/projects/{id}/messages/{messageId}/regenerate`——
   - `messages` 新增 `regeneratedFromMessageId`（nullable self-FK），建立新版本訊息時指向被取代的舊訊息
   - 重新走一次完整管線（`retrieving_sources → safety_check → streaming → completed`），沿用同一則使用者提問
   - UI 僅顯示最新版本（不做版本切換器，見 §10 範圍排除）
4. **頻率限制（C17）**：每帳號每日 30 則問答（跨該帳號所有專案累計，非單一專案），超量時 `sendMessage()` 直接拒絕並回 `RATE_LIMITED`（上游 §24 錯誤碼），文案溫和不指責（C17「超量溫和提示」）。`每月 10 份報告` 因 `reports` 功能未建置（A77 既定排除），本輪無法落地，僅登記待後續 `reports` 功能上線時一併補上限制。

## 2. 使用者角色

專案擁有者（一般使用者）：透過畫面操作對話、取消、重新產生，並看到頻率限制與安全提示的視覺回饋。

## 3. 操作流程

使用者進入專案 → 開啟／選擇對話 → 輸入問題送出 → 畫面即時顯示串流回答與引用 → 可取消或重新產生 → 達每日上限時送出鈕顯示溫和提示並擋下新提問。

## 4. 輸入資料

沿用 Sprint 15 已就緒的 `conversations`／`messages`／`message_citations`／`knowledge_chunks`／`observations`；本輪不新增資料來源，僅新增 `messages.regeneratedFromMessageId` 欄位。

## 5. 輸出結果

§1 四項交付；完成後使用者可從瀏覽器完整操作 SSE 串流問答（建立對話、提問、取消、重新產生），且系統對高頻使用有溫和防護。

## 10. 範圍排除

- **版本切換器 UI**——重新產生後 UI 僅顯示最新版本，不做「查看歷史版本」的介面，`regeneratedFromMessageId` 資料已保留、未來可延伸
- **「回報問題」功能**（上游 §21.1 提及但無進一步規格定義，§22.5 API 亦無對應端點）——無定義的資料模型與審核流程（C3 無管理 UI），且醫療安全急迫性低於本輪其他三項，留待後續視需要另立 DOR
- **`reports`（每月 10 份報告）頻率限制**——功能本身未建置（A77），無法落地限制，待 `reports` 功能上線時一併處理
- **進階安全過濾的自動攔截**——`safety_notice` 僅作為顯示提示，不自動阻擋或竄改回答內容，理由同 A73／A76：勉強做自動攔截且判斷不準確，比誠實顯示提示風險更高
- **語意層級引用一致性驗證**（技術選型 §11.5「claim 與引用段落一致」深度版本）——延續 Sprint 15 A74 既定範圍排除，需額外 NLI 模型或二次 LLM 呼叫
- **對話刪除／封存**——上游未明確要求本輪具備，且無资料保留政策決議，留待後續

## 11. 假設登記（待 PO 追認）

- **A78（新增）**：`regenerate` 採新增列模式（`regeneratedFromMessageId` 自我參照 FK），不修改舊訊息內容，比照專案既有「原值永遠保留」精神（憲法 §4，延伸自 `observations` 版本鏈 A42 的設計哲學）。UI 僅顯示最新版本，理由：版本切換器屬 UI 工程量較大的功能，本輪先確保資料正確保留，介面留待後續視需求評估。
- **A79（新增）**：頻率限制（C17）以「帳號」為計算單位、跨該帳號所有專案累計送出的使用者訊息數，非以單一專案計算。**理由**：C17 逐字為「每帳號每日 30 則問答」，且 LLM API 呼叫成本以帳號為計費／濫用防護單位較合理，比照 C7 登入鎖定「以 email 為單位」的既有設計精神類推至「以帳號為單位」。
- **A80（新增）**：`reports`（每月 10 份報告）部分的頻率限制本輪不實作。**理由**：`reports` 功能本身尚未建置（Sprint 15 A77 已排除，上游 §23 主要資料表亦無對應表），沒有可限制的對象；待該功能未來上線時，頻率限制邏輯應與其一併設計，非本輪能提前落地的部分。
- **A81（新增）**：`safety_notice` 於 UI 僅作視覺提示，不觸發自動攔截或內容過濾。**理由**：延續 A73／A76 一貫原則——關鍵字掃描的精準度不足以支撐「自動擋下」這種較強介入手段，強行攔截若誤判會讓使用者拿不到任何資訊，比誠實顯示提示、保留完整回答風險更高。
- **A82（新增）**：「回報問題」功能本輪不實作。**理由**：上游 §21.1 僅有一句「使用者可……回報問題」，無資料模型、無 API 端點、無審核流程規格；C3 既定「MVP 無管理 UI」，貿然做一個沒有後續處理流程的回報按鈕，使用者送出的回報不會有人看、等於是誤導性的功能承諾，違反誠實原則；留待後續視實際需求與審核機制另立 DOR。
- **A83（新增）**：`GET /conversations` 列表不分頁。**理由**：MVP 階段單一使用者的對話數量可控（比照既有 `documents`／`observations` 列表在資料量小的階段亦不分頁的既定模式），分頁機制留待資料量真正成長後再評估加入，避免過度設計。
