## 1. 需求描述

**範圍定位**：這是全案倒數第一個 Sprint，目標是把散落在 24 個 Sprint 裡「應該做但留到最後統一處理」的收尾項目集中完成，讓專案達到 MVP 可交付狀態。不是新增業務功能，而是「補齊安全缺口＋建立回歸信心＋讓文件真的可以交接」。

依 12_RELEASE_CHECKLIST.md 與上游 §33 Stage 11「強制驗收」，本輪範圍拆為五類：

1. **惡意檔案掃描**（KB-021 三次記錄留到本輪的缺口，上游 §27.3／§31 明列）：目前上傳僅有格式驗證（magic bytes）＋大小上限＋逾時防線（KB-022），完全沒有掃描檔案內容是否為已知惡意程式。本輪補上真正的掃描層。
2. **P0 e2e 測試**：現有 `tests/e2e/` 僅 3 個極簡 smoke 檔案（health／auth 頁面／首頁），未涵蓋任何跨模組黃金路徑。本輪補上關鍵黃金路徑的端到端測試（見 A143 範圍界定）。
3. **migration／rollback rehearsal**：`pnpm db:migrate`／`pnpm db:rollback` 至今每個 Sprint 都個別用過，但從未完整演練「16 筆 migration 全部套用→全部逐一回滾」這條完整鏈路。
4. **無障礙抽查**：WCAG 2.2 AA 為既定目標（憲法／SDD §11），至今未做過集中檢查，僅零星在各 Feature 開發時留意過對比度與可鍵盤操作。
5. **交付文件收尾**：`docs/runbook.md` 已有雛型（部署／回滾／金鑰輪替／事故處置），本輪檢查是否足供新維護者接手；另新增彙整版已知限制清單。

**明確排除、非本輪 AI 可完成範圍**（見 §10）：台灣個資與醫療服務法律審查（外部人工事項）、正式站真實資料庫還原演練（破壞性操作，見 A145）。

## 2. 使用者角色

- PO／未來接手的維運者：需要一份「已知這個系統目前的真實狀態（含限制）」的清單，以及一份能照著做就能重新部署／回滾的文件。
- 使用者（一般帳號）：本輪不新增使用者可見功能；唯一使用者可感受到的變化是「上傳的檔案現在會被實際掃描」。

## 3. 操作流程

- 惡意檔案掃描：使用者上傳檔案完成分段組裝後（既有 `completeUpload()` 流程），新增一道掃描步驟；掃描通過才轉入既有 `status="uploaded"`；掃描判定為惡意則轉 `upload_failed`（沿用既有狀態機，不新增狀態）並提示使用者。
- 其餘四類（e2e／migration rehearsal／無障礙抽查／文件收尾）皆為開發與維運內部流程，不涉及終端使用者操作流程變更。

## 10. 範圍排除

- **台灣個資與醫療服務法律審查**——上線硬門檻，但審查本身需要人類法律專業判斷，非 AI Agent 可完成的工作（A146）；本輪僅整理「待審查文件清單」（隱私權政策草稿、資料處理流程說明、既有 §27.3 安全措施清單）供 PO 另尋管道送審

- **自架 AV 掃描服務（如 ClamAV）**——採外部 API 而非自架服務，理由見 A142

## 11. 假設登記（待 PO 追認）

- **A142（新增，技術選型）**：惡意檔案掃描採 VirusTotal API（或等價的免費／低成本掃描 API），不自架 ClamAV 或等價服務。**理由**：本專案至今所有外部服務皆走「用受管 API，不自架基礎設施」的一貫路線（Supabase、Zeabur、OpenAI），自架掃描服務會新增維運負擔（版本更新、病毒碼更新、服務可用性自行負責），且與 KB-022 當時的決策精神一致（用最低成本解法對應威脅模型）；VirusTotal 提供免費額度，符合 MVP 階段規模。**待確認**：實際額度是否足夠本專案上線初期流量，需在實作時查證並誠實記錄於 SPRINT_LOG。
- **A143（新增，範圍界定）**：P0 e2e 測試聚焦三條跨模組黃金路徑（見 AC-4／AC-5／AC-6），不逐一窮舉上游 §30 Edge Cases／§31 Abuse Cases 清單。**理由**：Edge/Abuse Cases 中的絕大多數已被個別 Feature 的單元/整合測試覆蓋（如跨帳號存取、version conflict、重複提交等，每個 Feature 的 AC-8/AC-10 類測試皆已驗證），e2e 測試的獨特價值在於「證明跨模組串接真的能走通」而非重複驗證已被證明的單一模組規則；窮舉會讓本輪明顯超出 1 個 Sprint 預算。
- **A144（新增，執行環境）**：migration／rollback rehearsal 在本機獨立資料庫（非正式站共用資料庫）執行。**理由**：`db:rollback` 會 `DROP` 對應資料表，對正式站共用資料庫執行属破壞性操作，即使有備份也不應在非必要情況下觸碰生產資料；本機或臨時資料庫可達到同樣的「驗證 migration 鏈路可回滾」目的且零風險。
- **A145（新增，範圍限縮）**：「備份恢復演練」本輪不對正式站觸發真實還原操作，改為查證並記錄 Supabase 目前方案的備份／PITR 實際能力與限制。**理由**：真實還原是破壞性操作，且免費方案可能不支援 PITR（需查證），貿然演練有不可逆風險；先誠實記錄現況能力，若發現能力不足可作為 PO 決定是否升級方案的依據，比在不確定是否有安全還原路徑的情況下貿然嘗試更負責任。
- **A146（新增，範圍排除）**：台灣個資與醫療服務法律審查完全排除於本輪 AI 可完成範圍之外，不計入本輪 DOD。**理由**：法律審查需要人類法律專業判斷，AI Agent 不應也不能代為完成或宣稱完成；本輪僅整理待審查文件清單供 PO 另尋法律專業協助，這是唯一不阻塞在此 Sprint 內結案、但仍是上線硬門檻的項目（05_BACKLOG／12_RELEASE_CHECKLIST 皆已標註）。
- **A147（新增，文件形式）**：新增獨立精簡版 `KNOWN_ISSUES.md`，彙整 09_KNOWLEDGE_BASE.md 中仍開放（未解決）的已知限制，不要求 PO／未來維護者翻閱整本 KB 才能掌握現況。**理由**：09_KNOWLEDGE_BASE.md 累積 20+ 條目，多數是「已解決」的歷史記錄；上線交付需要的是「現在還有哪些已知限制」的快速掃視清單，兩者用途不同，分開維護較符合各自讀者需求。
- **A148（新增，抽查範圍）**：無障礙抽查選定 5–6 個代表性頁面（首頁／註冊登入／專案列表／戰情頁／計畫頁／對話頁），非逐頁全站稽核。**理由**：本專案十個工作區頁面共用同一套 UI 元件庫（`components/auth/auth-ui` 等既有共用元件），代表性頁面若通過，高機率其餘頁面因元件重用也一致合格；逐頁稽核在 1 個 Sprint 預算內不切實際，且與「MVP 不過度設計」原則（憲法／SDD §11）一致。
