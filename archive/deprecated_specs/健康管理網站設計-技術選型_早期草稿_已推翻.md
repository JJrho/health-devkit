# 健康管理網站設計－技術選型

## 1. 專案定位總結

本專案是一個以 50 歲以上族群為主要目標的「健康管理戰情表」網站／App。核心概念是讓使用者上傳年度健檢或每季抽血驗尿報告，系統協助整理健康指標、顯示趨勢、產生三個月情境模擬，並在需要時引導使用者尋求專業醫師建議。

本產品不應一開始定位為「AI 醫療診斷系統」，而應定位為：

> AI 健康資料整理、趨勢解讀、風險提醒與醫師溝通前置工具。

核心原則：

> AI 負責整理與提醒，醫師負責判斷與治療，使用者負責執行與追蹤。

---

## 2. 產品演進路線

### 初始階段：0 到 1

定位：

> 自用健康管理工具

目標是先讓個人使用者可以上傳自己的健檢 PDF，看到高齡友善、簡單安心的健康戰情表畫面。

此階段重點不在會員、不在雲端資料庫、不在正式 RAG，而是驗證：

- 使用者是否看得懂健檢資料整理結果
- Dashboard 是否有感
- 三個月情境模擬是否具備說服力
- 50 歲以上使用者是否覺得安心
- AI 建議是否不會被誤認為醫療診斷

---

### 成長階段

定位：

> AI 健檢報告解讀 SaaS

隨著使用者增加，逐步加入會員系統、資料保存、歷年趨勢、AI 分析紀錄與報告管理。

---

### 擴充階段

定位：

> 醫師 / 健康管理師輔助工具

當基礎穩固後，讓醫師或健康管理師可以查看 AI 整理後的摘要，進一步提供正式建議。

---

### 長期願景

定位：

> 50 歲以上會員制健康管理平台

當免費第一層使用者變多後，可逐步發展成醫師、健康管理師、中醫輔助觀點與個人化追蹤服務整合的平台。

---

## 3. 第一版設計方向

### 視覺定位

第一版 HTML 原型應該採用：

- 高齡友善
- 簡單
- 安心感
- 不像醫院系統
- 大字體
- 高對比
- 柔和背景
- 少資訊密度
- 按鈕清楚
- 避免過度醫療化與警告式語氣

建議風格：

- 米白
- 淺綠
- 暖灰
- 柔和藍綠
- 卡片式資訊區塊

避免：

- 過度冰冷的醫療藍
- 紅色警報滿版
- 太多表格與術語
- 像醫院 HIS 或病歷系統的介面

## 4. PDF 上傳與隱私策略

使用者希望第一版就可以上傳自己的 PDF，這是合理的，因為真實資料比假資料更能驗證產品感受。

但第一版建議採用：

> 本機 PDF 解析，不上傳伺服器，不儲存資料。

### 建議流程

```text
使用者選擇 PDF
    ↓
瀏覽器本機讀取 PDF
    ↓
前端嘗試抽取文字
    ↓
遮蔽姓名 / 身分證 / 電話 / 地址
    ↓
整理出疑似健檢指標
    ↓
顯示健康戰情表
    ↓
產生非醫療診斷的趨勢摘要與行動提醒
```

### 第一版應明確顯示的安心文案

```text
🔒 隱私模式已啟用

本次分析僅在你的裝置中進行。
PDF 不會上傳、不會儲存、不會進入資料庫。
重新整理或關閉頁面後，所有資料都會消失。
```

### 個資遮蔽原則

不顯示：

- 姓名
- 身分證字號
- 電話
- 地址
- 完整生日
- 完整病歷號
- 醫療院所識別編號

可顯示：

- 年齡區間
- 性別
- 檢查日期
- 健康指標
- 趨勢
- 風險提醒

範例：

```text
王小明 → 使用者 A
身分證字號 → 已遮蔽
生日 → 只保留年齡區間，例如 50-55 歲
電話 → 已遮蔽
地址 → 已遮蔽
醫院病歷號 → 已遮蔽
```

## 9. 第一層健康戰情表

第一層健康戰情表應分成五大區塊：

```text
1. 今日健康總覽
2. 主要風險指標
3. 三個月情境模擬
4. AI 行動提醒
5. 建議與醫師討論的問題
```

### 健康總覽卡片語氣

建議使用溫和提示，不要使用恐嚇式文字。

範例：

```text
血糖管理：需要注意
血脂狀態：偏高風險
肝功能：穩定
腎功能：目前正常
體重 / 體脂：建議追蹤
```

---

## 10. 三個月情境模擬

建議不要稱為「預測」，而是稱為：

> 三個月後的可能變化

原本的「最佳 / 一般 / 最差」可以改成更溫和的說法：

| 原始名稱 | 建議名稱 |
|---|---|
| 最佳狀況 | 積極執行 |
| 一般狀況 | 穩定執行 |
| 最差狀況 | 維持現況 |

### 範例表格

| 情境 | 三個月後可能變化 | 重點 |
|---|---|---|
| 積極執行 | 體重、腰圍、血脂可能改善 | 飲食、肌力、睡眠都穩定追蹤 |
| 穩定執行 | 部分指標維持或小幅改善 | 每週完成 60～70% 目標 |
| 維持現況 | 異常指標可能持續 | 建議先與醫師討論 |

## 11. AI 建議格式

每一則 AI 建議都應避免絕對化，建議採用以下格式：

```text
建議事項：
為什麼建議：
適合你的原因：
需要小心：
建議和醫師確認：
```

### 範例

```text
建議事項：
先從低衝擊運動開始，例如快走、腳踏車、簡單肌力訓練。

為什麼建議：
若體脂或 BMI 偏高，增加活動量可能有助於改善代謝指標。

適合你的原因：
相較於直接跑步，低衝擊運動對膝蓋、小腿與足底壓力較低。

需要小心：
若已有小腿、膝蓋、腳跟疼痛，不建議自行增加強度。

建議和醫師確認：
是否需要運動心電圖、物理治療師或專業教練評估。
```

## 12. 對健康建議風險的產品處理方式

### 12.1 落後指標問題

健檢報告是落後指標，因此系統應補上「領先行為指標」。

建議追蹤：

- 每日睡眠時數
- 每週運動次數
- 每週肌力訓練次數
- 含糖飲料次數
- 晚餐時間
- 體重腰圍變化
- 血壓自測
- 飲食紀錄
- 疼痛或疲勞紀錄

若三個月後沒有改善，系統應協助判斷：

```text
是建議本身不適合？
是執行率不足？
是運動方式造成傷害？
是睡眠壓力抵消效果？
是需要醫師檢查其他原因？
```

---

### 12.2 飲食與醫學資訊衝突

系統不應給出單一化建議，例如「多吃水果」或「每天喝咖啡」。

應採用條件化建議：

```text
不是「多吃水果」，
而是「根據血糖、三酸甘油脂、體重、脂肪肝風險，選擇水果種類、份量、時間與搭配方式」。
```

```text
不是「每天喝咖啡」，
而是「是否空腹、是否胃食道逆流、是否骨質疏鬆風險、是否睡眠品質差、是否有心悸」。
```

### 建議可信度欄位

| 建議 | 適用條件 | 不適用情境 | 需確認資料 |
|---|---|---|---|
| 增加蔬果 | 纖維不足、便秘、飲食單調 | 血糖控制差、三酸甘油脂高者需控份量 | HbA1c、TG、體重、飲食紀錄 |
| 咖啡攝取 | 無心悸、睡眠正常、非空腹 | 胃食道逆流、焦慮、睡眠差、骨鬆高風險 | 睡眠、骨密度、胃部症狀 |
| 增加運動 | 心肺與關節狀況允許 | 膝痛、足底痛、肌肉拉傷、姿勢不良 | 疼痛紀錄、運動類型、姿勢評估 |

---

### 12.3 運動與隱性傷害

AI 不應看到 BMI 或體脂偏高就直接建議跑步。

對 50 歲以上族群，建議先分層：

```text
第一層：是否有急性疼痛、胸悶、暈眩、關節痛？
第二層：是否適合低衝擊運動？
第三層：是否需要肌力、平衡、柔軟度優先？
第四層：是否需要物理治療師、教練或醫師評估？
```

第一版產品建議定位為：

> AI 不開具運動處方。AI 只產生「運動風險提醒」與「可與醫師 / 教練討論的問題清單」。

---

## 13. 中醫與紫微斗數的產品安排

### 中醫觀點

建議放在第二層或延伸觀點中，不放入第一版核心流程。

可定位為：

- 生活調養參考
- 食補方向
- 體質自我觀察
- 作息建議

文案應標示：

```text
中醫觀點作為生活調養參考，不能取代西醫診斷與治療。
```

---

### 紫微斗數 / 命理觀點

可作為品牌特色，但不能作為醫療判斷。

適合定位：

- 年度健康提醒
- 壓力與作息自我覺察
- 生活節律提醒

不建議：

- 疾病預測
- 壽命預測
- 某月份一定會生病

## 15. 主推方案

### 現階段主推

```text
單一 HTML 前端
+ 本機 PDF 解析
+ 匿名化顯示
+ Chart.js 視覺化
+ 不上傳伺服器
+ 不儲存資料
```

### 為什麼這是主推？

1. 最符合你目前「先看到效果」的需求。
2. 可以使用自己的 PDF，比假資料更有感。
3. 不需要一開始處理會員、資料庫、後端與 RAG。
4. 隱私風險相對低。
5. 對 50+ 使用者來說，安心感高。
6. 開發麻煩程度低。

## 16. 備選方案

### 方案 B：React + GitHub Pages

適合第二步。

| 項目 | 評估 |

| 適用階段 | 前端展示、作品集、Demo |

### 方案 C：Firebase + Zeabur

適合正式 MVP。

| 項目 | 評估 |
|---|---|
| 適用階段 | MVP 正式版、生產環境 |
| 前端 | React |
| 登入 | Firebase Auth |
| 資料庫 | Firestore |

不推薦作為主系統。

- SaaS
- 醫師後台

麻煩程度：

> 高，不複雜但非常麻煩。

## 17. 風險與應對策略

| 風險項 | 影響 | 應對策略 |
|---|---|---|
| AI 建議被誤認為醫療診斷 | 法規與安全風險高 | 明確標示「非診斷、非治療建議」，高風險項目轉醫師 |
| 健檢資料屬敏感個資 | 資安與隱私風險高 | 第一版不儲存；正式版需 Auth、Rules、同意書與刪除機制 |
| PDF 格式差異大 | 解析容易錯 | 第一版先以本機文字萃取為主，必要時允許手動修正 |
| 醫學資訊互相衝突 | 使用者困惑 | 每個建議附「適用條件 / 不適用情境 / 需確認資料」 |
| 三個月模擬被視為保證 | 期待落差 | 改稱「情境模擬」，不稱「預測」 |
| 運動建議造成傷害 | 高風險 | 先做風險篩檢，再提供醫師 / 教練討論清單 |
| 50+ 使用者操作門檻 | 使用率下降 | 大字體、少步驟、清楚色塊、不要太多術語 |

## 20. 最終結論

目前最適合的技術路線是：

```text
第一步：
單一 HTML + PDF.js + Chart.js + 本機解析 + 匿名化顯示

第二步：
React + Vite + Tailwind + GitHub Pages / Zeabur Static

第三步：
React + Firebase Auth + Firestore + Firebase Storage + Zeabur API + LLM

第四步：
加入 RAG、醫師後台、會員制、專業健康管理服務
```

現階段主推：

> 先做單一 HTML 的高齡友善健康戰情表原型。

原因：

- 最不麻煩
- 最快看到效果
- 能用自己的 PDF 測試
- 不急著碰會員與資料庫
- 隱私風險較低
- 符合自用健康管理工具的 0 到 1 階段
- 未來可以自然升級成 React、Firebase、Zeabur 與 SaaS

---

## 21. 一句話版本

> 這個產品應該先從「本機、不儲存、匿名化、高齡友善的健康戰情表 HTML 原型」開始，等產品體驗被驗證後，再逐步升級成 React 前端、Firebase 會員與資料庫、Zeabur 後端 API，最後才發展為 AI 健檢報告解讀 SaaS 與醫師輔助平台。
