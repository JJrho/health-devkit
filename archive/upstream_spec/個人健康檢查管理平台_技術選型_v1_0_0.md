# 個人健康檢查管理平台－技術選型 v1_0_0

> 對應產品規格：個人健康檢查管理平台規格 v1_0_0  
> 評估日期：2026-07-11  
> 目標市場：台灣  
> 主要客群：50–65 歲自主健康管理者  
> 架構原則：模組化單體、專案持久化、資料可追溯、最小權限、AI 全程串流、可逐步替換供應商

---

# 1. 文件結論

舊版技術選型需要重新評估，不能直接沿用。

舊版方案適合用來快速製作「單機、不保存資料的展示原型」，但目前產品規格已從單次報告展示，發展成需要長期保存與持續追蹤的健康管理平台，新增了：

- 帳號與 Google 登入
- 健康專案持久化與續編
- 多年健檔版本
- 文件背景解析
- 人工確認與稽核紀錄
- 健康行動計畫
- 日常回報
- 疼痛與不良反應
- 無改善檢討
- 醫學來源版本與衝突
- AI Streaming
- 資料匯出與刪除
- 未來專業人員協作

因此，新版正式 MVP 不應再以「單一 HTML＋瀏覽器本機 PDF 解析＋不保存資料」作為主架構。

## 1.1 建議主技術棧

| 層級 | 建議選型 |
|---|---|
| Web 前端 | Next.js App Router + React + TypeScript |
| UI | Tailwind CSS + 無障礙元件基礎層 |
| 表單 | React Hook Form + Zod |
| 圖表 | Apache ECharts 或 Recharts |
| 伺服器 API | Next.js Route Handlers／Server Actions 僅處理同步短任務 |
| 核心後端 | TypeScript 模組化單體；長任務由獨立 Worker 執行 |
| 資料庫 | PostgreSQL |
| ORM／Migration | Drizzle ORM 或 Prisma；本文件主推 Drizzle |
| 身分驗證 | Supabase Auth 或相容的受管 Auth；本文件主推 Supabase Auth |
| 物件儲存 | S3 相容私有 Object Storage；可先用 Supabase Storage |
| 背景工作 | Redis + BullMQ，或受管工作佇列 |
| AI | 模型供應商抽象層；第一版可接 OpenAI Responses API |
| AI 串流 | Server-Sent Events（SSE） |
| 醫學知識搜尋 | PostgreSQL Full-Text Search + pgvector，先混合搜尋 |
| 文件解析 | Parser Adapter；文字 PDF、掃描 OCR、表格解析分流 |
| 日誌與錯誤 | 結構化日誌 + Sentry 類錯誤監控；禁止健康內容進日誌 |

| API 契約 | OpenAPI 3.1 |
| 部署 | 台灣使用者低延遲區域的受管平台；Web、Worker、DB、Storage 分離 |
| CI/CD | GitHub Actions |
| 基礎設施管理 | 初期環境變數與平台設定；穩定後導入 Terraform/OpenTofu |

# 2. 為什麼規格文件不能取代技術選型文件

產品規格目前已定義：

- 功能範圍
- 使用流程
- 模組邊界
- API 概要
- 資料模型
- 狀態機
- 錯誤處理
- 非功能需求
- 驗收標準

但它刻意沒有綁定：

- 哪一個前端框架
- 哪一種資料庫
- 哪一套登入服務
- 哪一個雲端平台
- 哪一個 OCR 或模型供應商
- 具體的佇列、快取與監控工具

這是正確的文件分工。

## 2.1 產品規格負責回答

- 系統必須做什麼
- 使用者會看到什麼
- 資料如何變化
- 什麼情況算完成
- 什麼情況必須停止
- 哪些內容不能做

## 2.2 技術選型負責回答

- 用什麼工具實作
- 為什麼選它
- 代價與風險
- 哪些部分可替換
- 如何部署
- 如何測試
- 如何遷移
- 成本如何隨使用量增加

所以應保留一份獨立技術選型文件，並在重大產品邊界改變時更新。

# 3. 舊技術選型的逐項評估

## 3.1 可以保留的部分

### 高齡友善原則

保留：

- 大字
- 高對比
- 少資訊密度
- 清楚按鈕
- 溫和語氣
- 不使用滿版紅色
- 不做成醫院內部系統外觀

### PDF.js

可以保留為：

- 上傳前本機預覽
- 文字型 PDF 的初步文字層讀取
- 頁面渲染
- 原始位置標記

但不能再把 PDF.js 視為完整報告解析方案。

### 前端圖表

Chart.js 可用，但新版需要：

- 不同日期參考區間
- 可切換單位
- 可顯示大量時間點
- 鍵盤與資料表替代
- 可自訂 tooltip 與來源 drill-down

因此建議改用 ECharts；若團隊較熟 React，可用 Recharts，但複雜圖表彈性較低。

### 先做原型

仍然合理，但原型應分成：

1. 無真實健康資料的 UI 原型
2. 使用測試資料的可用性測試
3. 具正式資料模型的 MVP

不能把「一次性本機 Demo」直接演進成正式系統。

---

## 3.2 必須淘汰或改寫的部分

### 單一 HTML 作為正式起點

不適合作為新版 MVP 主架構。

理由：

- 新版有多頁流程
- 需要登入
- 需要專案狀態
- 需要表單續編
- 需要文件處理狀態
- 需要 Streaming
- 需要版本衝突
- 需要測試與模組切分

單一 HTML 可以保留為設計驗證物，不應成為正式程式基底。

### 不保存資料

與新版核心需求直接衝突。

新版必須支援：

- 以專案形式開啟
- 隔日繼續
- 歷年資料比較
- 行動計畫追蹤
- 日常回報
- 版本與稽核
- AI 報告過期判斷

因此正式 MVP 從 Stage 0 就必須有資料庫、Migration 與 Storage abstraction。

### 瀏覽器本機解析全部報告

不可作為主要解析管線。

原因：

- 掃描 PDF 沒有文字層
- 表格跨頁
- 版面與欄位差異
- OCR 與表格辨識耗資源
- 需要背景重試
- 需要解析版本
- 需要信心值
- 需要保留原始頁面座標

正確做法是：

- 瀏覽器：預覽與最小前處理
- 後端 Worker：解析、OCR、標準化
- 使用者：人工確認
- 系統：正式入庫與版本化

### Firestore 作為核心健康資料庫

不建議作為新版首選。

新版資料有大量關聯：

- 帳號與專案
- 文件與解析工作
- 辨識項目與正式紀錄
- 正式紀錄版本鏈
- AI 訊息與引用
- 行動計畫、行動、指標、回報與檢討
- 知識來源、段落、主張與衝突
- 刪除依賴與稽核

這些關聯、交易、唯一約束、版本查詢與稽核需求更適合 PostgreSQL。

Firestore 並非不能實作，但會增加：

- 跨集合一致性處理
- 關聯資料重複
- 複雜查詢成本
- 刪除依賴管理
- 報表與稽核困難

### 「三個月情境模擬」

應從技術需求中移除。

不再實作：

- 積極執行後的數值預測
- 一般執行後的數值預測
- 維持現況後的健康預測

改為：

- 有效且安全
- 尚未有效或無法判斷
- 出現不適或需專業評估

這是規則與行動分支，不是數值預測模型。

### Firebase + Zeabur 作為預設正式架構

可以實作，但不再是最適合的預設方案。

主要問題不是平台品質，而是新版需要：

- 關聯資料
- 長任務
- 文件與 AI 工作佇列
- 交易
- RLS／專案隔離
- 向量與全文混合搜尋
- 稽核
- 後續專業人員權限

PostgreSQL 為中心的架構會更一致。

# 4. 架構形態

## 4.1 主推：模組化單體 + 獨立 Worker

第一版不要拆成微服務。

```text
┌──────────────────────────────────────────┐
│ Next.js Web                              │
│ UI、登入流程、同步 API、SSE Proxy        │
└─────────────────────┬────────────────────┘
                      │
┌─────────────────────▼────────────────────┐
│ Core Application                         │
│ Auth / Projects / Documents /            │
│ Observations / Dashboard / Plans /        │
│ Knowledge / Conversations / Audit         │
└──────────────┬───────────────┬───────────┘
               │               │
       ┌───────▼───────┐ ┌────▼───────────┐
       │ PostgreSQL    │ │ Object Storage │
       │ + pgvector    │ │ Private files  │
       └───────┬───────┘ └────────────────┘
               │
       ┌───────▼───────────────────────────┐
       │ Queue + Worker                    │
       │ OCR / Parsing / Indexing /        │
       │ Reports / Export / Deletion       │
       └───────────────────────────────────┘
```

## 4.2 為什麼不是微服務

目前：

- 團隊尚小
- 產品仍需驗證
- 模組很多，但流量未知
- 健康資料的一致性比獨立擴展更重要
- 過早分散部署會增加權限、觀測與交易難度

模組化單體仍應：

- 依領域分目錄
- 只透過明確 service/repository 介面呼叫
- 禁止跨模組直接改資料表
- 背景工作使用明確 job contract
- 模型、OCR、Storage 可替換

# 5. Web 前端選型

## 5.1 主推：Next.js App Router + TypeScript

### 選擇原因

- 適合公開 Hero Page 與登入後工作區共存
- 支援 Server Components 與 Streaming UI
- Route Handlers 使用標準 Request／Response
- 可在同一 Repository 維護 UI、同步 API 與 BFF
- React 生態完整
- TypeScript 有利維持 API 與資料模型一致

### 使用邊界

Next.js 處理：

- 頁面
- 表單
- 使用者互動
- 上傳工作建立
- 同步 CRUD
- SSE 連線
- 讀取戰情資料

Next.js 不直接執行：

- 大型 OCR
- 多頁 PDF 深度解析
- 長時間知識索引
- 長時間匯出
- 大量刪除
- 長時間 AI 後處理

以上交由 Worker。

## 5.2 UI

### Tailwind CSS

適合：

- 快速建立一致 Design Token
- 大字、高對比與 Responsive
- 不需要先引入重型元件框架

### 元件策略

建議採：

- Headless／Accessible primitives
- 自建 Design System wrapper
- 不把特定 UI 套件的 API 散落全專案

必要元件：

- Button
- Input
- Select
- Dialog
- Drawer
- Tabs
- Toast
- Progress
- Data table
- File preview
- Chart wrapper
- Streaming response region

## 5.3 表單與驗證

- React Hook Form
- Zod
- 前後端共用 schema
- 所有健康欄位允許不確定與缺值
- 不以預設值冒充使用者資料

## 5.4 圖表

主推 Apache ECharts。

原因：

- 多軸與區間呈現
- 大量時間序列
- 自訂 tooltip
- 圖形縮放
- 資料區域選擇
- 參考區間與不同單位呈現彈性較高

規定：

- 每張圖都有等價資料表
- 不只靠顏色
- 縮放保持資料比例
- 原報告參考區間按日期呈現

# 6. 身分驗證選型

## 6.1 主推：Supabase Auth

用途：

- Email／密碼
- Google 登入
- Email 驗證
- Session 管理
- 密碼重設

### 選擇原因

- 可與 PostgreSQL 整合
- 支援 Google 與 Email 登入
- 可用 JWT claims 配合資料庫隔離
- 初期可減少自建驗證風險
- 未來仍可替換為其他 OIDC 供應商

## 6.2 強制設計

- 應用層驗證專案權限
- 資料庫層使用 RLS 或等價防禦
- Service Role 只能存在伺服器
- 不讓瀏覽器直接讀取任意健康資料表
- Google 身分不可只信任前端顯示資料
- 帳號連結需有明確規則
- Session 支援撤銷
- 敏感操作可要求重新驗證

## 6.3 備選

- Auth.js + 自有 PostgreSQL session
- Google Cloud Identity Platform
- Firebase Auth

若已經有 Firebase 團隊經驗，可使用 Firebase Auth，但核心資料庫仍建議 PostgreSQL。

# 7. 資料庫選型

## 7.1 主推：PostgreSQL

理由：

- 完整交易
- 外鍵與唯一約束
- 複雜關聯
- 樂觀鎖定
- JSONB 可保存解析中間資料
- Full-Text Search
- pgvector
- Row-Level Security
- 成熟備份與恢復工具
- 適合稽核、版本與刪除依賴

## 7.2 主要資料類型

- UUID 主鍵
- timestamptz
- numeric，避免健康數值使用浮點誤差
- jsonb，用於來源座標、解析原文與可擴充 metadata
- enum 或受約束文字
- soft delete timestamp
- integer version

## 7.3 RLS

RLS 作為第二層防禦，不取代應用層授權。

每個健康資料資源必須能追到：

```text
current_user
  → project membership
  → project_id
  → resource
```

禁止只依前端提供的 project_id。

## 7.4 ORM

主推 Drizzle ORM。

理由：

- Schema 與 SQL 關係透明
- 適合 PostgreSQL 原生能力
- Migration 可審查
- 不妨礙使用 RLS、索引、pgvector 與複雜 SQL

Prisma 仍是可接受備選，但遇到資料庫原生能力時可能需要較多 raw SQL。

# 8. 檔案儲存

## 8.1 主推：S3 相容私有 Object Storage

第一階段可使用 Supabase Storage。

儲存：

- 原始 PDF
- 原始圖片
- 預覽圖片
- 解析中間產物
- 匯出報告

## 8.2 規則

- Bucket 預設 private
- 使用短效 signed URL
- 上傳後掃描
- 儲存 checksum
- 使用不可猜測 object key
- 不把使用者原始檔名當 object key
- 原始檔與預覽檔分開
- 刪除使用 background job
- 備份與資料庫版本需能對應
- 日誌不得記錄 signed URL

## 8.3 上傳方式

- 瀏覽器先本機預覽
- 伺服器建立 upload session
- 大檔使用 multipart／resumable upload
- complete endpoint 需 idempotency key
- 完成後建立 background parse job

# 9. 文件解析選型

## 9.1 不綁定單一 OCR

建立 `DocumentParser` 介面：

```ts
interface DocumentParser {
  canHandle(input: DocumentInput): Promise<boolean>;
  parse(input: DocumentInput): Promise<ParsedDocument>;
}
```

解析管線：

```text
檔案安全檢查
  → 檔案分類
  → 文字型 PDF 文字層
  → 掃描 PDF／圖片 OCR
  → 表格與欄位抽取
  → 檢驗項目候選
  → 單位與參考區間解析
  → 信心值
  → 人工確認
```

## 9.2 建議工具分工

- PDF.js：瀏覽器預覽
- 伺服器 PDF 文字抽取工具：文字層
- OCR Provider Adapter：掃描影像
- LLM／文件模型：只協助結構化，不直接成為正式資料
- 規則引擎：數字、單位、日期與參考區間驗證

## 9.3 第一版解析策略

先支援：

- 文字型 PDF
- 清晰掃描 PDF
- JPG／PNG
- 常見血糖、血脂、肝功能、腎功能、尿酸與尿液項目

解析結果必須保存：

- 原始文字
- 頁碼
- 座標
- Parser 版本
- 信心值
- 使用者修正紀錄

# 10. 背景工作與佇列

## 10.1 主推：Redis + BullMQ

工作類型：

- 文件解析
- OCR
- 預覽產生
- 檢驗項目標準化
- 知識索引
- AI 報告產生
- 匯出
- 資料刪除
- 報告 stale 更新

## 10.2 強制規則

- 每個 Job 有 idempotency key
- 最多重試次數
- 指數退避
- Dead-letter／failed 狀態
- Job payload 不放完整健康內容
- 只傳 resource ID
- Worker 重新讀取授權範圍內資料
- 可取消的 AI 工作保存 cancellation token
- 重試不得重複建立正式紀錄

## 10.3 備選

- 雲端受管 Queue
- PostgreSQL-based queue

若初期不想維護 Redis，可先用 PostgreSQL queue，但需保留 Queue Adapter。

# 11. AI 與 RAG 選型

## 11.1 模型介面

建立 `LLMProvider`：

```ts
interface LLMProvider {
  stream(request: LLMRequest): AsyncIterable<LLMEvent>;
  cancel(runId: string): Promise<void>;
}
```

不得讓業務模組直接呼叫特定模型 SDK。

## 11.2 第一版模型

可先採 OpenAI Responses API，原因：

- 支援 Streaming
- 支援結構化輸出與工具呼叫
- 可由伺服器處理
- 適合建立模型供應商 Adapter

但產品不能依賴模型保存健康狀態。正式狀態保存在自有資料庫。

## 11.3 Streaming

主推 SSE。

事件：

- stream_started
- retrieval_completed
- content_delta
- citation_added
- safety_notice
- stream_completed
- stream_cancelled
- stream_failed

前端：

- 可取消
- 可重連
- 依 sequence 去重
- 中斷保留已完成內容
- 不對每個 token 觸發螢幕閱讀器朗讀

## 11.4 RAG

第一版不需另購獨立向量資料庫。

使用：

- PostgreSQL Full-Text Search
- pgvector
- Metadata filter
- Reranking Adapter

知識查詢順序：

```text
有效來源篩選
  → 適用地區／族群篩選
  → 關鍵字全文搜尋
  → 向量搜尋
  → 合併與 rerank
  → 衝突主張檢查
  → 引用驗證
```

## 11.5 引用驗證

AI 完成前驗證：

- citation target 存在
- knowledge source 為 active
- observation 屬於目前 project
- 被引用資料未刪除
- claim 與引用段落一致
- 不允許模型自行產生 URL 作為來源

# 12. 健康行動規則引擎

AI 不應獨立決定計畫是否安全。

建立可版本化的規則層：

- 必填健康背景
- 活動安全前置資訊
- 飲食限制條件
- 停止規則
- 不良反應規則
- 無改善分類
- 轉介條件
- 緊急提示

AI 可：

- 將規則結果轉成白話
- 產生可選行動草稿
- 提醒缺少資料

AI 不可：

- 覆寫規則
- 自行增加強度
- 自行改藥
- 將命理結果輸入健康規則

規則版本必須跟計畫一同保存。

# 13. API 與契約

## 13.1 API

- REST JSON API
- `/api/v1`
- OpenAPI 3.1
- ISO 8601 UTC
- 統一 error envelope
- 所有 mutation 支援 idempotency key
- 可修改資源包含 version
- 分頁使用 cursor

## 13.2 同步與非同步

同步：

- CRUD
- 專案切換
- 表單儲存
- 戰情查詢
- 建立 Job

非同步：

- 解析
- OCR
- 知識索引
- AI 報告
- 匯出
- 大量刪除

## 13.3 版本衝突

使用：

```http
If-Match: "<version>"
```

或 request body version。

衝突回傳：

```json
{
  "code": "VERSION_CONFLICT",
  "message": "此資料已在其他位置更新",
  "retryable": false
}
```

# 17. 部署建議

## 17.1 環境

- local
- test
- staging
- production

不得共用：

- Database
- Storage bucket
- Auth project
- AI API key

## 17.2 部署單元

- Web
- Worker
- PostgreSQL
- Redis／Queue
- Object Storage

## 17.3 區域

優先選擇：

- 台灣使用者延遲低
- 可簽署合適資料處理條款
- 支援備份、加密與存取控制
- 能清楚掌握資料儲存區域

正式上線前須完成台灣個資與醫療服務法律審查。

## 17.4 推薦平台組合

### 組合 A：快速 MVP

- Web／Worker：Render、Railway、Fly.io 或同類受管平台
- DB／Auth／Storage：Supabase
- Redis：Upstash 或平台 Redis
- AI：OpenAI API

優點：

- 快速
- 維運負擔低
- PostgreSQL、Auth、Storage 整合

風險：

- 需確認區域與資料處理條款
- 需避免把所有邏輯綁定平台專屬 API

### 組合 B：較高控制

- Web／Worker：Google Cloud Run
- DB：Cloud SQL PostgreSQL
- Storage：Cloud Storage
- Queue：Cloud Tasks／Pub/Sub
- Auth：Identity Platform
- AI：供應商 Adapter

優點：

- 元件與權限控制完整
- 適合未來正式營運

缺點：

- 初期設定與成本較高

## 17.5 本文件主推

MVP 先採組合 A，但所有外部服務都經 Adapter，避免平台鎖定。

- AI Token
- 向量索引
- Worker 運算
- 出站流量
- 備份

控制方式：

- 上傳大小與頁數限制
- 解析前 checksum 去重
- 已確認資料不重複 OCR
- 知識段落 embedding 去重
- AI 問答使用必要資料，不送完整歷年文件
- 取消 Streaming 後停止模型工作
- 設定使用者與專案配額
- 低成本模型處理分類，高能力模型處理複雜分析
- 正式內容保存結果與引用，不反覆重新生成

不應在尚未取得實際使用量前寫死月費數字。

# 21. 明確不採用

## 21.1 不採用單一 HTML 作為正式產品架構

只允許作為無資料 UI Prototype。

## 21.2 不採用純前端保存健康資料

正式資料只能保存於受控後端。

## 21.3 不採用 Firestore 作為核心正式資料庫

除非未來團隊有強烈既有能力與完整資料模型驗證。

## 21.4 不採用獨立向量資料庫作為第一版必需品

先使用 PostgreSQL + pgvector。

## 21.5 不採用微服務

先用模組化單體與 Worker。

## 21.6 不採用 AI 自動診斷、開方或健康結果預測

AI 只負責整理、解釋、草稿與引用。

## 21.7 不採用紫微斗數作為健康資料輸入

命理產品與健康產品資料庫完全分離。

# 22. 備選方案

## 22.1 若團隊偏 Python

可將 Worker 改成：

- Python
- FastAPI 或純 Worker
- Celery／Dramatiq
- OCR／資料處理 Python 生態

Web 與同步 API 仍可使用 Next.js。

適合：

- OCR 與資料科學工作量高
- 團隊熟悉 Python
- 需要大量文件處理套件

代價：

- 多語言 Repository
- 型別與契約需 OpenAPI／Schema 管理
- 部署與觀測多一套

第一版若只有一位開發者，建議先全 TypeScript；OCR Provider 可由外部服務完成。

## 22.2 若必須使用 Firebase

建議：

- Firebase Auth：可保留
- Firebase Storage：可保留
- PostgreSQL：仍作核心資料庫
- Worker：獨立部署
- 不使用 Firestore 作為主要關聯資料庫

# 24. 重新評估觸發條件

以下任一情況發生，需更新本文件：

- 活躍使用者超過目前架構容量
- 每日文件解析量顯著增加
- 需要正式醫師或中醫師協作
- 進入正式通訊診療
- 增加家庭代理權限
- 新增行動 App
- 新增穿戴裝置
- 改變主要 AI 或 OCR 供應商
- 需要跨區域部署
- 法規要求改變
- PostgreSQL、Storage 或 Queue 成本不合理
- 資料必須限定特定地區保存

# 25. 最終建議

新版規格已經不再是「先做一個本機健檔 Dashboard 看效果」的產品。

正確的第一版技術定位是：

> 以 PostgreSQL 為資料核心、以健康專案為持久化邊界、使用 Next.js 提供高齡友善介面、以獨立 Worker 處理文件與長任務、以 SSE 串流 AI 回答，並用明確 Adapter 隔離 Auth、Storage、OCR、Queue 與模型供應商的模組化健康管理平台。

舊版原型仍可保留作為視覺參考，但不應成為正式 MVP 的程式基礎。
